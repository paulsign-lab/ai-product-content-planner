# review-harvest - 경쟁 제품 리뷰 수집 (02번 파일)

> `{out}` = 이번 프로젝트의 결과 폴더 `outputs/<제품명>_<날짜>/` 입니다. 단독 실행할 때는 가장 최근 폴더를 쓰고, 둘 이상이라 모호하면 먼저 묻습니다. (`skills/README.md` 참고)

소비자가 **스스로, 먼저 한 말**을 읽어 옵니다. 일반 웹 조회로는 보이지 않는 리뷰 위젯을 브라우저로 읽는 단계입니다.
이 스킬이 만드는 것은 분석이 아니라 **근거가 붙은 원자료**입니다. (분석은 `insight-synthesis`)

## 사전 준비 - 경로 선택
- **경로 1 (브라우저 수집):** 브라우저 도구가 연결되어 있을 때. `/mcp`에서 Playwright(기본) 또는 claude-in-chrome이 연결되어 있는지 확인한다. **로그인하지 않은 깨끗한 브라우저**일 것. Claude in Chrome이면 새 프로필을 쓰라고 안내한다.
- **경로 2 (붙여넣기):** 브라우저 도구가 없거나, 사이트가 접속을 막았거나, 사용자가 직접 읽고 싶을 때. 아래 "붙여넣기 경로"를 따른다. **연결이 없다고 02단계를 건너뛰지 않는다.**
- 사이트마다 경로를 섞어도 된다(예: 3곳은 브라우저, 1곳은 붙여넣기).

## 입력값
- `{out}/01_site_scan.md`의 사이트별 URL, 리뷰 위젯 종류, 총 리뷰 수
- (선택) 수집 상한. 기본: **사이트당 상품 1개, 상품당 최대 30건, 그중 1~3점 최소 8건 이상 목표**

## 붙여넣기 경로 (경로 2)
1. 사용자에게 안내한다: "상품 페이지의 리뷰 영역에서 **고별점 약 10건, 낮은 별점(1~3점) 약 10건**을 복사해 붙여 넣어 주세요. 낮은 별점은 페이지의 정렬 메뉴에서 '낮은 별점순'을 고르면 됩니다. **이름과 사진은 빼고** 별점, 시기, 본문만 붙여 주세요."
2. 사이트(경쟁사)마다 한 번씩 받는다. 받은 원문은 작업 폴더의 `{out}/02_reviews_input.md`에 저장한다.
3. 이후 STEP 3~5와 같은 형식으로 정리하되, 수집 방법 칸에 `수동 붙여넣기`로 적고 **읽은 건수는 붙여 넣은 건수**로 기록한다.
4. 이름이 섞여 있으면 요약 파일에는 옮기지 않는다고 알린다.
5. 붙여넣기 경로에서도 인용은 약 125자 이내로, 출처 URL은 사용자가 알려 준 상품 페이지 주소로 적는다.

## 수집 예절 (반드시 지킨다. 어기지 않는다)
1. 로그인하지 않는다. 공개 페이지만 읽는다. 로그인벽, 캡차, 접속 차단이 나오면 **멈추고 `ACCESS FAILED`로 기록**한다. 우회하지 않는다.
2. **한 번에 한 사이트, 순서대로.** 페이지 이동 사이에 2~3초 이상 쉰다. 동시에 여러 탭을 돌리지 않는다.
3. 리뷰어 **이름, 사진, 프로필은 수집하지 않는다.** 별점, 작성 시기, 본문만.
4. 본문은 요약하되, 인용은 **약 125자 이내**로 출처 URL과 함께. 긴 원문 전체를 저장하지 않는다.
5. 산출물 상단에 "사이트 약관이 자동 수집을 제한할 수 있다. 확인과 책임은 사용자에게 있다"를 적는다.

## 실행 절차

### STEP 1 - 상품 페이지를 열고 리뷰 영역까지 내려간다
페이지를 열고 3초 기다린 뒤, 리뷰 영역이 나타날 때까지 천천히 스크롤한다(위젯은 늦게 뜬다). 총 리뷰 수와 평점 분포가 보이면 기록한다.

### STEP 2 - 위젯별로 읽는 방법
(아래는 힌트입니다. 사이트가 바뀌면 화면 구조를 보고 판단합니다.)

| 위젯 | 읽는 방법 | 저별점 보는 법 |
|---|---|---|
| **Okendo** | 리뷰 목록 항목의 본문 | 정렬 드롭다운에서 `Lowest Rating` 선택 |
| **PowerReviews** | 리뷰 본문 영역 | 정렬에서 `Lowest Rated` 선택 |
| **Yotpo** | 리뷰 본문 영역 | 별점 필터나 정렬이 있으면 사용 |
| **Bazaarvoice** | 페이지에 구조화 데이터(JSON-LD)로 일부 리뷰가 들어 있는 경우가 많다. 화면의 "더 보기"로 추가 | 정렬/필터 메뉴가 있으면 사용 |
| **Judge.me, Stamped 등** | 리뷰 본문 영역 | 별점 필터 |

### STEP 3 - 별점별로 따로 읽는다 (핵심)
- 기본 화면은 높은 별점이 많다. 그것만 읽으면 불만이 보이지 않는다. 순서:
  1) 기본 화면에서 **고별점 리뷰 약 10건**
  2) 정렬을 **낮은 별점순**으로 바꿔 **1~3점 리뷰 약 8~10건**
- 정렬이나 필터가 없는 사이트는 "저별점 읽기 실패(정렬 없음)"로 기록한다. **저별점이 적다고 불만이 없다고 쓰지 않는다.**
- 각 리뷰마다 기록: `별점 / 대략의 시기 / 한 줄 요약 / 짧은 인용(<=125자)`.

### STEP 4 - 표본 품질 표시
각 리뷰에 해당하면 태그를 붙인다.
- `체험단`: "무료로 받았다", "in exchange for my honest review", "complimentary" 등
- `타제품 혼입`: 다른 제품(예: 클렌저) 이야기가 섞인 경우
- `제품 외 불만`: 배송, 세금, 관세, 고객 응대 (제품 문제와 분리)
- `브랜드 응대 있음`: 브랜드가 답글을 단 경우 (응대 방식은 인사이트의 힌트)
- `언어`: 영어 외 리뷰는 원어 표기 후 번역은 `[추정]`

### STEP 5 - 수집 로그
사이트별: 읽은 건수(고/저별점), 정렬 방법, 실패 사유, 전체 리뷰 대비 읽은 비율.

## 산출물
**`{out}/02_reviews.md`** - 상단 고지(약관, 표본 한계) + 사이트별 수집 로그 + 별점별 리뷰 요약표(짧은 인용, 태그, 출처 URL)
> 개인을 식별하는 정보는 넣지 않는다.

## 핸드오프
- <- `site-scan` (URL, 위젯, 총 리뷰 수)
- -> **`insight-synthesis`**: 리뷰 요약표 전체
- -> **`claims-check`**: 고객이 쓴 건강, 효능 표현(우리가 쓰면 안 되는 말) 참고

## 작성 원칙
- 읽은 것만 기록한다. **건수, 별점, 인용을 지어내지 않는다.**
- 표본은 "관찰된 경향"이다. "대부분의 고객이 ~한다"는 쓰지 않는다.
- 막히면 우회하지 말고 기록한다. 기록된 공백이 지어낸 완성보다 낫다.
